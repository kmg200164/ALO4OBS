# 하위 에이전트 병렬 실행과 모델 배정

큰 작업을 비싼 모델 하나로 끝까지 돌리지 않고, 메인 에이전트가 총괄·검수만 하면서 세부 작업은 알맞은 모델과 노력량의 하위 에이전트에게 나눠 맡기는 방법이다. 2026-10-06 명기 요청으로 ALO4OBS 0.8.0 작업에서 만들었고, 어떤 작업에든 쓴다.

## 쓰는 법

작업 지시문 맨 위에 아래 블록을 붙여 넣는다. 모델 이름은 버전 없이 opus·sonnet·haiku 별칭으로 적어서, 그때 쓸 수 있는 최신 모델로 맞춰지게 한다. Codex처럼 모델 별칭이 다른 도구에서는 "가장 강한 모델 / 보통 모델 / 가벼운 모델"로 읽는다.

```text
[작업 방식: 하위 에이전트로 나눠서 병렬 실행]
너(메인 에이전트)는 이 작업의 총괄이야. 직접 다 하지 말고 아래 원칙대로 하위 에이전트(Task)에 나눠 맡기고, 결과를 검수하고 합쳐.

1. 먼저 계획부터
- 시작 전 확인(git 상태, pull, 기준 빌드·테스트)은 네가 직접 한다.
- 그다음 저장소 구조를 읽고, 아래 지시문의 항목들을 "어떤 파일을 고치는지" 기준으로 묶은 실행 계획표를 만들어 보여 줘. 표에는 묶음 이름, 맡을 항목, 고칠 파일, 병렬 가능 여부, 배정 모델·노력량을 넣는다.
- 계획표를 보여 준 뒤 바로 진행해도 된다(승인 기다리지 않아도 됨). 단 계획과 크게 달라지면 다시 알려 줘.

2. 병렬과 순서 규칙
- 같은 파일을 고치는 작업은 절대 동시에 돌리지 않는다. 한 파일은 한 번에 한 에이전트만 맡는다.
- 겹치는 파일이 많은 작업(i18n 문자열, README, 공통 설정·상태 코드 등)은 한 에이전트에 묶거나 순서대로 돌린다.
- 읽기만 하는 작업(검색 목록 만들기, 구조 점검, 하드코딩 값 찾기, 현황 표 만들기)은 먼저 병렬로 돌려서 결과를 모아 둔다.
- 기본 흐름: (가) 조사 묶음 병렬 → (나) 파일이 안 겹치는 수정 묶음만 병렬, 겹치면 순서대로 → (다) README·CHANGELOG·문서는 코드 수정이 끝난 뒤 한 에이전트가 한 번에 → (라) 실제 브라우저·앱 검증과 최종 빌드·테스트는 맨 마지막.

3. 모델·노력량 배정 기준
- opus, 노력량 높음: 계산·알고리즘·배치 로직 변경, 상태·저장·복원·데이터 구조 변경, 원인을 모르는 버그 수정, 보안·권한 관련, 최종 통합 검수
- sonnet, 노력량 보통: 일반 UI·i18n 수정, 문서 다시 쓰기, 테스트 추가, 점검 보고서 작성
- haiku, 노력량 낮음: 검색 목록 만들기, 문자열 단순 치환, 파일명·형식 바꾸기, 목록·라이선스 표기 추가, 줄 수 세기
- 애매하면 한 단계 높은 모델을 쓴다. 하위 에이전트가 두 번 실패하면 같은 작업을 한 단계 높은 모델로 다시 맡긴다.

4. 하위 에이전트에 줄 지시
- 각 에이전트에게 맡을 항목 원문(지시문에서 해당 부분), 고쳐도 되는 파일 목록, 건드리면 안 되는 파일, 끝나고 돌릴 테스트를 함께 준다.
- 커밋·push·태그·Release·배포는 하위 에이전트도 절대 하지 않는다(지시문이 따로 허락한 경우만 예외).
- 각 에이전트는 바꾼 파일, 돌린 테스트와 결과, 확인 못 한 것을 짧게 보고한다.

5. 메인 에이전트의 검수
- 하위 에이전트 결과를 받을 때마다 diff를 직접 읽고, 지시문과 다르거나 공통 규칙을 어긴 곳은 고치게 한다.
- 모든 묶음이 끝나면 시작 때와 같은 빌드·테스트를 직접 다시 돌려 기준 결과와 비교한다.
- 최종 보고는 지시문의 보고 형식을 따르고, 맨 앞에 "어떤 묶음을 어떤 모델·노력량으로 돌렸는지" 표를 붙인다.

아래가 작업 지시문 전문이야.
```

## 주의

- 작은 작업(파일 몇 개, 한두 단계)에는 붙이지 않는다. 나누고 검수하는 비용이 더 크다.
- 하위 에이전트를 쓸 수 없는 도구라면 이 블록의 "계획표 → 조사 먼저 → 파일 단위 순서 → 마지막 통합 검수" 순서만 따른다.
